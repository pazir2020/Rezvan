# ثبت نفرساعت تولید تیم‌های رضوان — نسخه افزایشی LAN

## محدوده
- هر رکورد متعلق به یک سفارش تنور، تیم آهنگری یا بنایی منتسب به همان سفارش و تاریخ مشخص است.
- نفرساعت موظفی، نفرساعت اضافه‌کاری و نفرساعت توقف خارج از اختیار جدا ثبت می‌شوند. علت اضافه‌کاری و توقف، در صورت وجود، اجباری است.
- فقط ثبت‌های تاییدشده در گزارش تجمیعی لحاظ می‌شوند؛ وضعیت pending/rejected و تعداد آن‌ها مشخص است.
- کاربر دارای write_records ثبت می‌کند؛ کاربر دارای approve_records تأیید/رد می‌کند. ثبت‌کننده نمی‌تواند ردیف خود را تأیید کند. ردیف تعیین‌تکلیف‌شده بدون فرایند اصلاح رسمی قفل است.
- هیچ داده‌ای خودکار از حضور و غیاب، حقوق، فیش، کارانه یا ساعت قانونی کارکنان تولید/ویرایش نمی‌شود.
- این ماژول بهره‌وری قطعی یا «کم‌کاری» را تشخیص نمی‌دهد؛ برای آن، زمان استاندارد نوع تنور، خروجی سالم و ثبت مستقل وقفه‌ها لازم است.

## روش کار
1. قبل از کار با ماژول در محیط آزمایشی از PostgreSQL بکاپ تأییدشده تهیه کنید.
2. همان روش ارتقای اسکیمای فعلی با دستور `python -m app.cli init-db` را اجرا کنید؛ دو جدول جدید `oven_team_hours` و `oven_team_hours_events` با `CREATE TABLE IF NOT EXISTS` اضافه می‌شوند.
3. ابتدا سفارش‌ها و تیم‌های سازنده در «رهگیری ساخت تنور» ثبت شوند؛ ثبت نفرساعت برای تیمی که در سفارش منتسب نیست رد می‌شود.
4. در «نفرساعت و اضافه‌کاری تیم» نفرساعت روزانه را برای آن سفارش وارد و برای بازبینی ارسال کنید.
5. فرد مجاز مستقل از ثبت‌کننده، رکورد را تأیید یا رد می‌کند. مجموع ساعات تنها بر اساس داده تأییدشده نمایش داده می‌شود.

## قواعد حسابرسی و محدودیت‌ها
- واحد اندازه‌گیری «نفرساعت جمع اعضای تیم» است، نه ساعت تقویمی ساخت یا ساعت یک نفر. از ثبت همزمان ساعات یک تیم در چند سفارش خودداری کنید؛ گزارش موارد روزانه غیرمعمول را علامت می‌زند.
- کار معمول یک تیم چهار نفره با ۸ ساعت موظفی روزانه حدود ۳۲ نفرساعت است؛ تنها یک فرض نمایشی برای هشدار است، نه ساعت قانونی قطعی. شیفت، تعطیلات و برنامه واقعی باید بررسی شوند.
- نفرساعت مؤثر تحلیلی = موظفی + اضافه‌کاری - توقف ثبت‌شده؛ این شاخص بدون سنجش نتیجه استاندارد، بهره‌وری نیست.
- تأیید ردیف نفرساعت به معنی تأیید پرداخت قانونی اضافه‌کاری یا کارانه نیست؛ اینها سازوکار مجزا دارند.
- همان کلید (سفارش، نوع تیم، روز) نمی‌تواند دوبار ثبت شود. برای اصلاح پیش از تأیید از API PUT با version استفاده می‌شود؛ نسخه UI اولیه صرفاً ثبت جدید و تأیید/رد را نمایش می‌دهد.
- پس از تأیید، اصلاح نیازمند روند مدیریتی جداگانه است؛ از تغییر دستی DB پرهیز کنید.
- آزمون واقعی SQL و مرورگر سرور شرکت فقط پس از استقرار آزمایشی ممکن است.
